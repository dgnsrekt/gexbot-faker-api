# GEXBot Faker — Endpoint Compatibility Audit (2026-08-09)

**Question:** if we load last Friday (2026-08-07) for replay and serve it, do we
return the same responses the real GexBot API returns now?

**Short answer:** **Response bodies — yes, exactly.** Every served data endpoint
emits byte-for-byte the same field set as the live API, with zero field drift
since the July snapshot. **But the faker is not yet a drop-in replacement:** its
*auth mechanism* and its *GEX path segments* diverge from the real API, so a
client coded against the real API gets `400`s from the faker before it ever sees
a body.

## Method

Three sources reconciled:

1. **Fresh live probe** of `api.gex.bot` (this audit) → `live-probes/2026-08-09.json`
   — top-level response fields per endpoint, sanitized (no values, no secrets).
2. **Prior live probe** `live-probes/2026-07-19.json` — to detect drift over time.
3. **Upstream OpenAPI** `upstream-openapi.yaml` (repo `nfa-llc/gexbot-openapi`,
   unchanged since July — fresh-clone SHA matches the recorded source SHA).

Faker responses captured from the running stack serving `2026-08-07` (last Friday).

## Finding 1 — Response bodies are fully compatible ✅

Three-way field diff (Jul 19 real · Aug 9 real · faker), all served endpoints:

| Endpoint | Jul19 | Aug9 | faker | Verdict |
|---|---|---|---|---|
| `GET /tickers` | 3 | 3 | 3 | faker == real |
| `GET /{t}/classic/{cat}` | 15 | 15 | 15 | faker == real |
| `GET /{t}/classic/{cat}/majors` | 10 | 10 | 10 | faker == real |
| `GET /{t}/classic/{cat}/maxchange` | 8 | 8 | 8 | faker == real |
| `GET /{t}/state/{cat}` | 10 | 10 | 10 | faker == real |
| `GET /{t}/orderflow/orderflow` | 37 | 37 | 37 | faker == real |

- **No field drift** in the real API between July and August.
- The response **shape is index-independent** — every replay row carries the same
  schema, so "seek to the last index" returns the same structure as any other row.
- **Caveat on the upstream spec as an oracle:** it is exact for `classic` /
  `majors` / `maxchange`, but documents `state` with the generic `basic_response`
  schema and `orderflow` with a superset `orderflow_response`. For those two, the
  live probe (not the spec) is the correct oracle — and the faker matches the
  probe. Do not treat the upstream schema as ground truth for `state`/`orderflow`.

## Finding 2 — Auth mechanism diverges ❌ (highest priority)

| | Real API (Aug 2026) | Faker |
|---|---|---|
| Mechanism | `Authorization: Basic <key>` (also `Bearer`) **header** | `?key=<key>` **query param** |
| Missing-auth status | `400` | `400` |
| Missing-auth body | `{"error":"Authorization header not found."}` | `parameter "key" in query has an error: value is required but missing` |

The faker **ignores** the `Authorization` header entirely and **requires** a
`key` query param the real API doesn't use. A client written against the real API
authenticates by header → the faker rejects it with `400`. (Note: the July probe
recorded these endpoints as open; they now require header auth — an upstream
tightening.)

## Finding 3 — GEX path segment diverges ❌

| Category kind | Real API path | Faker path | Faker on real name |
|---|---|---|---|
| classic/state GEX | `.../gex_zero`, `.../gex_one`, `.../gex_full` | `.../zero`, `.../one`, `.../full` | `400` (enum reject) |
| state greeks | `.../gamma_zero`, `.../delta_zero`, … | same | ✅ matches |

The faker stripped the `gex_` prefix from GEX categories in the URL (enum
`[full, zero, one]`) while keeping full names for greeks. Real API uses full
category names everywhere. So `/SPX/classic/gex_zero` → `400` on the faker.

Classified `missing` in `matrix.json`; real-API field shapes captured where available:

## Recommendations (priority order)

1. **Auth parity (Finding 2)** — accept `Authorization: Basic/Bearer <key>` and
   return the real `{"error":"Authorization header not found."}` on absence.
   Decide whether to keep `?key=` as a compatibility alias. *This unblocks every
   real-API-coded client.*
2. **GEX path parity (Finding 3)** — accept `gex_zero`/`gex_one`/`gex_full` in the
   path (alias or rename the enum). Highest-churn client-facing break after auth.
3. **Body-schema regression test** — extend the `compatibility` harness to assert
   each served endpoint's response fields against the live-probe fixture (turns
   this manual audit into CI). Oracle = probe, not upstream schema.
4. **Fill coverage (Finding 4)** — start with `/hist/eod/{ticker}` (data already
   on disk) and the cheap public metadata routes (`/{package}/categories`,
   `/tickers/quant`).
